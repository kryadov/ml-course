# План на 12 месяцев: от корпуса до релиза LLM-моделей

**Профиль:** разработчик, ML почти с нуля · 5–7 ч/нед · ~12 месяцев · железо: 2× NVIDIA Tesla L4 (24 ГБ каждая, суммарно 48 ГБ) + сервер · облако — эпизодически под большие прогоны.

**Составлено:** 22 июля 2026.

---

## 0. Сразу о двух развилках

**Scikit-Learn ≠ трек к LLM.** Scikit-Learn — это классический ML (табличные данные, регрессии, деревья, кластеризация). Для тренировки LLM он почти не используется: там стек PyTorch + Hugging Face (Transformers, Datasets, PEFT, TRL) + инструменты файнтюна (Unsloth / Axolotl) + инференс (vLLM) + MLOps-обвязка. Но Scikit-Learn стоит пройти как **месяц-фундамент**: он даёт интуицию про фичи, метрики, переобучение, валидацию — без этого дальше будет каша. Так что он в плане есть, но как ступень, а не как основа.

**Про ваше железо.** 2× L4 (48 ГБ) — это по-настоящему хорошо для такого трека. Реалистично на нём:
- инференс моделей до ~30–34B (квантованные) через vLLM;
- QLoRA-файнтюн моделей 7–14B на одной карте, 32B — на двух с FSDP;
- полный fine-tune (не LoRA) моделей до ~1–1.5B;
- обучение «своей маленькой» LLM с нуля (10–100M параметров) — на выходных.

Облако (RunPod / Vast / Lambda, ~$0.5–2/час за A100/H100) понадобится 3–4 раза за год под конкретные тяжёлые прогоны — заложите ~$50–150 суммарно, не подписку.

## 1. Как устроен весь путь модели (карта, к которой возвращаемся)

Чтобы «разобраться от формирования корпуса до релизов», держим в голове полный жизненный цикл. Каждая фаза плана закрывает один-два его блока:

1. **Данные:** сбор корпуса → очистка/дедупликация → фильтрация качества → токенизация → форматирование под задачу.
2. **Обучение:** предобучение (pretraining) → дообучение под инструкции (SFT) → выравнивание (DPO/RLHF) — или, чаще на практике, только SFT/LoRA поверх готовой открытой модели.
3. **Оценка:** метрики, бенчмарки, ручной ревью, red-teaming, проверка на утечки.
4. **Упаковка и инференс:** квантизация, оптимизация, сервинг (vLLM), API.
5. **MLOps/LLMOps:** версионирование данных и моделей, трекинг экспериментов, CI/CD, реестр моделей, деплой.
6. **Эксплуатация:** мониторинг (дрифт, качество, стоимость), сбор обратной связи, обновление/дообучение, релизы новых версий.

Цель года — пройти этот цикл целиком минимум дважды на реальных доменах.

## 2. Фазовый план (12 месяцев, ~6 фаз по ~2 месяца)

Темп рассчитан на 5–7 ч/нед. В каждой фазе: что учим → что делаем руками → артефакт, который остаётся в портфолио.

### Фаза 1 (мес. 1–2). Фундамент: Python для данных + классический ML + окружение

**Учим:**
- NumPy, pandas, работа с табличными данными; matplotlib/seaborn для разведки.
- Scikit-Learn: train/val/test split, кросс-валидация, метрики (accuracy/precision/recall/F1, ROC-AUC), переобучение и регуляризация, пайплайны.
- Базовая математика по мере надобности: градиентный спуск, что такое лосс, производная как «направление улучшения» (не углубляйтесь в доказательства — достаточно интуиции).
- Настройка железа: драйверы NVIDIA, CUDA, PyTorch с GPU, проверка что обе L4 видны (`nvidia-smi`, `torch.cuda.device_count()`), Docker для воспроизводимости.

**Делаем руками:**
- Проект на Scikit-Learn: классификация транзакций на «нормальные / подозрительные» (табличный датасет фрода) — это первый заход в ваш фин-домен, но на классике. Полный цикл: EDA → фичи → модель → метрики → отчёт.
- Настроить рабочий репозиторий: git, структура проекта, `requirements.txt`/`uv`, Makefile, pre-commit.

**Артефакт:** репозиторий с классическим ML-пайплайном и README; рабочее GPU-окружение на сервере.

**Ресурсы:** курс Kaggle Learn (Python, Pandas, Intro to ML, Intermediate ML — бесплатно, быстро); документация Scikit-Learn (User Guide).

### Фаза 2 (мес. 3–4). Нейросети и трансформеры: как LLM устроена внутри

**Учим:**
- PyTorch: тензоры, autograd, обучающий цикл, Dataset/DataLoader.
- От перцептрона к трансформеру: эмбеддинги, внимание (attention), позиционные кодировки, декодер, авторегрессия.
- Токенизация (BPE), что такое «контекст», лосс на предсказание следующего токена.

**Делаем руками (ключевое):**
- **Пройти Karpathy «Zero to Hero»** и собрать nanoGPT/nanochat — обучить крошечную GPT с нуля на своём корпусе (например, тексты спецификаций из фин-домена или сборник инструкций к препаратам). Обе L4 позволят обучить 10–50M модель за часы. Это и есть «формирование корпуса → токенизация → обучение → генерация» в миниатюре, но полностью своими руками.

**Артефакт:** своя мини-LLM с нуля + конспект «как работает трансформер» своими словами.

**Ресурсы:** Andrej Karpathy — «Neural Networks: Zero to Hero» и nanochat (тренировка LLM с нуля, есть разборы); PyTorch official tutorials.

### Фаза 3 (мес. 5–6). Данные и файнтюн готовых моделей (сердце практики)

**Учим:**
- Hugging Face экосистема: Transformers, Datasets, Tokenizers, PEFT (LoRA/QLoRA), TRL (SFT/DPO).
- Формирование корпуса «по-взрослому»: сбор, очистка, дедупликация (MinHash), фильтрация качества, разметка, форматы инструкций (chat template).
- LoRA vs QLoRA vs полный файнтюн; выбор базовой модели; инструменты Unsloth (быстро, экономно по памяти) и Axolotl (гибкие конфиги).

**Делаем руками:**
- **Проект №1 — text2sql (обязательный).** Взять code-специализированную базу (Qwen-Coder или актуальный аналог) и зафайнтюнить QLoRA на парах (схема+вопрос → SQL) из ваших схем, примеров и открытых бенчмарков (BIRD/Spider). Полный цикл данных: собрать корпус пар → почистить → добавить few-shot/retrieval схемы → обучить на L4 → мерить **execution accuracy** против базовой модели. Здесь же собрать retrieval схемы (schema linking) — он даёт прирост качества больше, чем сам файнтюн.
- Освоить Hugging Face «smol course» / рецепты файнтюна как шаблон процесса.

**Артефакт:** первая доменная SQL-модель + датасет пар + retrieval схемы + карточка модели (model card) с execution accuracy.

**Ресурсы:** Hugging Face LLM Course и smol-course; гайды по Unsloth/Axolotl (QLoRA рецепты).

### Фаза 4 (мес. 7–8). Оценка, выравнивание, RAG

**Учим:**
- Оценка LLM: бенчмарки, LLM-as-a-judge, ручной ревью, проверка на галлюцинации и утечки, метрики под задачу (точность извлечения, F1 для NER).
- Выравнивание: DPO (проще RLHF), когда нужно, как собрать пары предпочтений.
- RAG: эмбеддинги, векторные БД, retrieval — часто даёт больше пользы, чем файнтюн, для доменных знаний.

**Делаем руками:**
- Добавить к SQL-модели из Фазы 3 **оценочный харнесс** (execution accuracy на отложенных запросах) и, по желанию, **RL/DPO-проход** с наградой за успешное выполнение запроса (подход Arctic-Text2SQL-R1 / Think2SQL — так мини-модель догоняет крупные).
- **Обучить вторую модель — summary-модель:** вход = вопрос + таблица результатов SQL, выход = текстовое саммари. Отдельный датасет, отдельная метрика — **faithfulness** (сверка чисел в тексте с таблицей, антигаллюцинация).
- Собрать сквозной пайплайн: retrieval схемы → SQL-модель → выполнение → summary-модель. Сравнить связку с single-model подходом.

**Артефакт:** две связанные модели (SQL + summary) + оценочные отчёты по обеим метрикам + сквозной прототип.

## 3. Домены для реальных моделей

Ваши три + альтернативы. Для каждого — почему подходит, тип задачи и где брать открытые данные.

### A. Финтех / процессинг (ваш вариант — хорошо ложится на LLM)
- **Задачи:** классификация/нормализация транзакций; NLP по документации вендора и спецификациям (напр. ISO 8583, ISO 20022); RAG-ассистент по спекам процессинга; извлечение полей из платёжных сообщений; объяснение кодов ответов/отказов.
- **Данные:** публичные спецификации стандартов, датасеты детекции фрода (Kaggle), синтетические платёжные сообщения (можно генерировать самому — это отдельный полезный навык). Реальные данные вендора внутренние — но методику отработаете на открытых/синтетических.
- **Плюс:** близко к вашей работе, есть где применить; текстовая доменная специфика идеальна под доменный файнтюн + RAG.

### B. Фарма / лекарства (ваш вариант — отличный, богатые открытые данные)
- **Задачи:** NER по инструкциям (действующее вещество, дозировка, побочки); извлечение нежелательных реакций (ADE); классификация взаимодействий; RAG по регуляторике.
- **Данные (открытые, качественные):** openFDA (drug labels, adverse events), DrugBank, RxNorm, датасет TAC 2017 Adverse Reactions, OnSIDES, бенчмарк MultiADE.
- **Плюс:** самый «датасет-богатый» из трёх — легко собрать чистый корпус, много готовых бенчмарков для честной оценки.

### C. Обложки треков по аудио (ваш вариант — интересный, но это НЕ LLM)
- **Важно:** это **мультимодальная генерация** (audio → image), а не языковая модель. Стек другой: аудио-эмбеддинги (CLAP) + диффузионная модель (Stable Diffusion, дообучение через LoRA/DreamBooth). Многие MLOps-практики те же (данные, трекинг, сервинг), но обучение и оценка — про диффузию и картинки, не про текст.
- **Как встроить:** отличный **бонус-проект после Фазы 5** — покажет, что MLOps-контур переносится и на генеративку. Пайплайн: аудио → извлечь эмбеддинг/жанр/настроение → сгенерировать промпт → диффузия → обложка. Но не делайте его основным LLM-треком.
- **Данные:** аудио с тегами жанра/настроения + парные обложки; исследования SonicDiffusion, гайды по файнтюну SD под album cover.

### D. Text2SQL — генерация SQL + саммари по данным (ОБЯЗАТЕЛЬНЫЙ, приоритетный)

Это идеальный домен для маленькой специализированной модели: задача узкая, есть чёткая проверяемость (запрос либо выполняется и даёт верный результат, либо нет), богатые открытые бенчмарки. У вас уже есть схемы, примеры запросов и документация — это ровно тот корпус, который нужен.

**Ключевое решение: да, это должны быть ДВЕ разные модели.** Причины:

1. **Генерация SQL** и **саммаризация данных** — разные задачи, разные базовые модели и разные метрики. Совмещение в одной модели тянет качество вниз у обеих.
2. **SQL-модель:** база — code-специализированная (семейство Qwen-Coder или аналог актуальный на старте), генерация детерминированная (temperature 0), структурированный вывод, привязка к схеме. Метрика — execution accuracy (выполнился ли запрос и совпал ли результат).
3. **Summary-модель:** база — обычная instruct-модель, вход = вопрос пользователя + таблица результатов, выход = связный текст. Главная метрика — **верность цифрам** (faithfulness, отсутствие галлюцинаций), а не «код выполнился». Это про беглый естественный язык, а не про синтаксис.
4. **Практика:** разделение даёт независимую итерацию (улучшаете SQL, не ломая саммари), разный тюнинг под разные требования, и summary-модель может быть даже меньше / заменена на API.

**Архитектура пайплайна (важнее, чем «просто зафайнтюнить»):**

```
вопрос → [1. Schema linking / RAG]  → отобрать релевантные таблицы+колонки
                                       + подтянуть few-shot похожих примеров запросов
       → [2. SQL-модель (finetuned)] → сгенерировать SQL (temp 0)
       → [3. Выполнить + self-correct] → если ошибка выполнения, вернуть ошибку модели на 1 ретрай
       → [4. Summary-модель]          → таблица результатов + вопрос → текстовое саммари
```

Отдельно подчеркну: **на качество SQL сильнее всего влияет не сам файнтюн, а подача схемы в контекст** (schema linking + retrieval нужных таблиц/колонок + few-shot примеры). Схемы меняются — RAG по схеме позволяет не переобучать модель на каждое изменение. Файнтюн закрепляет диалект, стиль ваших запросов и специфику; retrieval даёт актуальную структуру. Лучшие результаты 2026 (напр. Arctic-Text2SQL-R1 от Snowflake) показывают, что **маленькая модель + обучение с подкреплением по execution-награде** обгоняет крупные — то есть ваш кейс «мини-модель с высоким качеством» абсолютно реалистичен.

- **Данные:** ваши схемы + примеры запросов + документация (основной корпус) + открытые бенчмарки для базы и оценки: **BIRD** (реалистичный, с «грязными» БД), **Spider / Spider 2.0** (кросс-доменный), Text2SQL augmentation-фреймворки для расширения обучающих пар.
- **Обучение:** старт — SFT на парах (схема+вопрос → SQL); продвинутый уровень — RL с наградой за успешное выполнение запроса (execution-based reward, подход Think2SQL / Arctic-R1).
- **Оценка:** execution accuracy на отложенных запросах по вашим схемам + отдельный харнесс faithfulness для summary-модели (сверка чисел в тексте с таблицей).
- **Где в плане:** делаем это **Проектом №1 в Фазе 3** (вместо абстрактного домена) — он обязательный и хорошо структурирован; summary-модель добавляем в Фазе 4 (там же оценка и выравнивание). MLOps-контур в Фазе 5 оборачивает уже связку из двух моделей + retrieval + исполнение SQL — получается полноценный продукт.

### Дополнительные варианты доменов (с хорошими открытыми данными)
- **Юридический/договоры:** извлечение пунктов, классификация рисков, RAG по нормативке (датасеты CUAD, LEDGAR). Богатые данные, чёткие задачи.
- **Поддержка/тикеты:** классификация обращений, авто-ответы, суммаризация диалогов (много открытых датасетов саппорта).
- **Код-ассистент под ваш стек:** файнтюн на вашем кодовом стиле/либах — практично и легко собрать корпус из своих репозиториев.
- **Научные статьи/биомед:** суммаризация и Q&A по PubMed — пересекается с фармой, тот же источник данных.

**Рекомендация по выбору:** **text2sql — обязательный Проект №1** (узкая проверяемая задача, идеальна для мини-модели, у вас уже есть корпус). Вторым доменом — **фарма** (богатые данные) или **финтех** (близко к работе). Обложки — мультимодальный бонус в конце. Так вы закроете и «понять LLM целиком», и «сделать реальные модели с высоким качеством», и увидите, где заканчивается язык и начинается генеративка.

## 4. Технологический стек (что реально держать в руках)

- **Язык/база:** Python, PyTorch, NumPy, pandas, Scikit-Learn (фундамент).
- **LLM-обучение:** Hugging Face Transformers, Datasets, PEFT (LoRA/QLoRA), TRL (SFT/DPO); **Unsloth** (память/скорость) и/или **Axolotl** (конфиги). На старте выберите один — вероятно Unsloth под L4.
- **Модели-основы:** актуальные малые открытые модели на момент старта фазы (семейства Qwen, Llama, Gemma — проверяйте свежие релизы, картина меняется каждые пару месяцев).
- **Оценка:** свой харнесс + LLM-as-judge; для NER/извлечения — precision/recall/F1; для **text2sql — execution accuracy** (сравнение результата выполнения), для summary — faithfulness.
- **Text2SQL специфика:** code-база (Qwen-Coder), schema linking / retrieval схемы, execution-based reward для RL, песочница для безопасного выполнения запросов (read-only), отдельная summary-модель.
- **RAG:** sentence-transformers/эмбеддинги + векторная БД (Qdrant/Chroma).
- **MLOps:** DVC (данные), MLflow или W&B (эксперименты + реестр), Docker, GitHub Actions (CI/CD).
- **Инференс:** vLLM (сервинг на L4), FastAPI (API), квантизация GPTQ/AWQ.
- **Мониторинг:** логирование запросов, метрики качества/стоимости, простой дашборд (Grafana или встроенное в W&B).

## 5. Бюджет и железо

- **Основное — ваши 2× L4 (48 ГБ).** Покрывают ~90% плана: файнтюн до 14B (QLoRA), инференс, обучение мини-LLM с нуля, диффузия для обложек.
- **Облако — эпизодически.** Понадобится 3–4 раза под тяжёлое: файнтюн модели 30B+, длинный претрейн-эксперимент, быстрый бенчмарк на A100/H100. RunPod / Vast.ai / Lambda, почасовая аренда. **Оценка на год: ~$50–150 суммарно**, не подписка. Всегда останавливайте инстанс после прогона.
- **Хранилище:** корпуса и чекпоинты растут быстро — заложите на сервере запас под данные (десятки–сотни ГБ) и настройте DVC-remote (S3-совместимый бакет или локальный).

## 6. Принципы, чтобы не сойти с трека

Учитесь через проект, а не «сначала вся теория». Каждую фазу заканчивайте артефактом в репозитории — портфолио важнее конспектов. Не гонитесь за размером модели: маленькая обученная и задеплоенная модель ценнее большой, которую вы не смогли запустить. RAG часто побеждает файнтюн для «знаний» — всегда сравнивайте оба подхода. Ведите эксперименты в трекере с первого файнтюна, а не «потом внедрю MLOps» — иначе потеряете воспроизводимость. И проверяйте актуальность моделей/инструментов на старте каждой фазы: в LLM всё устаревает за месяцы.
